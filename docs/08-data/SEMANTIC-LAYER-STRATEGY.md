# 语义底座战略（Semantic Layer Strategy）

状态：v1 设计基线；无生产授权。本文定义本项目「语义底座层」的采用范围、方法映射与接口约定。理论源头：《本体驱动的AI数据管理》（分析见 [ONTOLOGY-BOOK-ANALYSIS](../14-research/ONTOLOGY-BOOK-ANALYSIS.md)）。

## 1. 定位与边界

**语义底座**是组织层、协议层、资产层之下的第四层基座：让 50 个 AI 岗位与外部数据源共享同一套业务语义（概念、术语、关系、规则、权限语义），使「机器懂业务」从口号变为可契约化、可校验、可演进的资产。

```
治理层：八阶段协议 + PILOT-G0~G4 门禁 + 授权位（全部 false）
度量层：双层 KPI（L1 GMV 当期 / L2 品牌资产长周期）
能力层：SKL-* Skill 契约（JSON Schema 机器可读）
场景层：20 场景规格（八阶段+门禁推进）
组织层：50 岗位 Role Profile + Soul + Playbook + Preset
─────────────────────────────────────────────
语义底座层（本层）：业务本体·术语表·事理规则·权限语义·资产目录语义
```

**本期边界（先方法后技术）**：只产出 Markdown 语义契约、术语表、规则模板与就绪度标注；不生成 RDF/OWL 文件、不引入语义数据库、不接入真实数据。技术栈选型（SKOS-lite→OWL→SWRL 的升级路径）在 FLOW-09 试点验证后再评估。

## 2. 采用范围：轻量语义层四件套

| 组件 | 载体 | 对应书中规范 | 本项目落点 |
| --- | --- | --- | --- |
| 术语表（SKOS-lite） | `docs/08-data/glossary/` Markdown + 受控词表 JSON | SKOS | Momcozy 品牌域核心术语（商品/SKU/渠道/订单/库存/品牌资产指标/人群） |
| 对象-关系模型（OWL-lite） | Markdown 表 + JSON Schema | OWL/RDF | 核心业务对象、属性、关系的轻量形式化（不涉推理机） |
| 事理规则（SWRL-lite） | 「如果…那么…」自然语言+触发条件模板 | SWRL | 场景规格中的业务规则显性化；进 Policy Gate 前的规则候选 |
| 权限语义（ODRL-lite） | 授权位语义声明扩展 | ODRL | Service Identity/Scope 的语义化描述；权限策略的「谁-对什么-在什么条件下」三元组 |

**明确不做**：区块链六证明（远期对照，见书评 §3）、语义数据库部署、多模态本体、自动化本体推理。

## 3. FFA → 八阶段协议映射

书中「事实–事理–行动」一体化模型与本项目八阶段协同协议同构，可作为对外叙事与内部校验的双视角：

| FFA 层 | 本项目对应 | 说明 |
| --- | --- | --- |
| 事实层（发生了什么） | STG-01~03 输入/证据 + Stage Artifact | 业务对象状态、数据事实、验收产物 |
| 事理层（为何发生/将导向何方） | STG-04~06 分析/决策/门禁规则 | 业务规则、因果链、约束、KPI 口径 |
| 行动层（做什么/如何闭环） | STG-07~08 Action Intent→Policy Gate→Execution Broker→反馈 | 可执行动作、权限约束、执行回执、复盘优化 |

**用法**：场景规格评审时用 FFA 三问校验完整性——「事实从哪来（语义是否对齐）？事理规则是否显性化？行动是否可控可回滚？」语义底座的产出物（术语/对象/规则/权限语义）分别注入三层。

## 4. 分层治理 → 授权位映射

书中「本体约束+AI 智能+人类监督」三支柱与分层治理，与本项目授权体系同构：

| 书中层级 | 本项目对应 | 语义底座提供物 |
| --- | --- | --- |
| 顶层：人类掌控战略与红线 | 授权位全 false + 用户拍板（D 系列决策） | 红线规则的语义化表述（什么绝不能做） |
| 中层：人在回路监控 | HITL 复核点 + 高风险分级逐对象审批 | 「需人工确认」的权限语义声明 |
| 底层：规则内自主运行 | 设计态 Case 推演、预期 NoActionRecord | 「可自主执行」的权限语义声明（远期） |

**用法**：授权位不再只是布尔开关——每个授权位翻转时，须同时声明其语义策略（允许的对象范围/条件/时效/回收规则），语义声明与授权位一一对应、版本化绑定。

## 5. 场景本体就绪度标准

对照书 §8.1.3 优选/排除标准，给 20 场景打三维标注（详见 [ONTOLOGY-READINESS](../03-scenarios/ONTOLOGY-READINESS.md)）：

- **优选（优先建模）**：跨域语义协同、规则推理明确、高合规——如 SCN-002（覆盖缺口诊断）、SCN-009（品牌资产评估）、SCN-016（结算对账）
- **可选（按需建模）**：语义复杂度中等或规则部分明确——如 SCN-010/011/012/013/015
- **不建议（暂不建模）**：高频动态变化、规则模糊、简单低价值——如 SCN-017（资金，规则虽明确但动作层风险最高、语义收益低先验证）、SCN-019/020（管理基建，语义对象少）

**原则**：先做诊断型/对账型（零外部动作）场景验证语义层价值，再扩展到建议型，受控动作型最后。

## 6. 与既有契约的接口约定

| 既有资产 | 语义底座接口 |
| --- | --- |
| FLOW-09-DATA-CONTRACT | 数据字段补充「语义标签」（对应术语表条目 ID）；契约头部声明依赖的本体模块 |
| FLOW-09-SERVICE-IDENTITY-SCOPE | Scope 声明补充权限语义三元组（主体/客体/条件/时效） |
| SKL-BRAND-* Skill 契约 | Skill 声明 `ontology_dependencies`：所需术语集/对象集/规则集（最小必要加载） |
| 场景规格（SCN-*.md） | 新增「事理规则」小节：核心规则按「如果…那么…」格式列出，标注来源（显性文档/专家经验） |
| Role Playbook | 岗位知识萃取使用「29 句话」模板（见 [KNOWLEDGE-ELICITATION-29](KNOWLEDGE-ELICITATION-29.md)） |
| 双层 KPI | L2 品牌资产指标绑定术语表条目，保证口径语义一致 |

## 7. 演进路径

```
本期（方法先行）：术语表 + 轻量对象/关系/规则 + 权限语义声明 + 就绪度矩阵
    ↓ FLOW-09 试点验证（P1 诊断 Case 消费语义层）
下一步：试点场景的事理规则形式化验证 + Skill ontology_dependencies 实际加载测试
    ↓ 多场景验证后
远期（技术选型）：评估是否升级 SKOS→OWL-lite→语义数据库；区块链六证明仅作对照不采用
```

## 8. 风险与边界

- 语义底座不替代数据契约：契约管「能读什么字段」，语义层管「字段是什么意思」；两者版本化独立演进。
- 「29 句话」依赖业务专家（本项目中由用户承担）投入；试点阶段先跑通 AGT-029+SCN-002 一例再评估推广成本。
- 术语表是活资产：随场景规格和数据契约演进同步更新，设术语评审责任人（建议 AGT-029 立言或 AGT-047 数据治理岗）。
- 全部 DESIGN_ONLY：语义契约不构成数据接入、权限开通或生产授权。
