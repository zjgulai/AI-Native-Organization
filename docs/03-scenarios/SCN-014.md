# SCN-014：订单、交付与渠道异常

状态：v1 设计规格；场景候选映射待企业验证。AI结果负责人：FLOW-03（供需：补货、采购与交付）绑定时为 AGT-016 知量；FLOW-04/FLOW-05/FLOW-07 绑定时以该流结果负责人为准（BVS-01 现为 AGT-023）。依据：D-025、D-026、D-078、PB-003、PB-005、PB-007。

适用说明：本场景是**四流绑定**的最广场景——订单异常、交付异常、渠道异常分别触及 FLOW-03（交付职权，主绑定）、FLOW-04（渠道准入/同步）、FLOW-05（客户沟通）、FLOW-07（升级为重大事件）。按 D-025 一张 Case 只背一条主流的结果责任，其余经 `correlation_id` 拆分；异常升级为账号健康事件时转 SCN-018 的 FLOW-07 Case（如物流时效恶化推高 ODR/LSR）。本场景的核心产出不是「处理掉异常」，而是**把异常定位到环节并把根因反馈回上游**——它是 FLOW-03/04/05 的异常收敛器。

## 经营目的与范围

把订单、交付与渠道异常转化为**可定位、可分派、可闭环、可反哺的异常处理流程**，减少异常对 GMV、客户体验与账号健康的三重损失。

- 业务对象：订单状态异常（卡单/未确认/超时未发）、配送异常（延误/丢件/破损/清关滞留）、渠道异常（库存同步失败/Listing 抑制/跟卖/渠道 API 故障/价格同步冲突）；不含正常补货采购决策（SCN-006/007）、客服话术本身（SCN-015）、账号绩效指标治理（SCN-018）。
- 范围内：异常信号检测 → 环节定位（下单→支付→仓储→承运→清关→末端→渠道同步）→ 分级处置 → Action Intent 执行 → 根因分类与反馈。
- 范围外：不直接操作 ERP/WMS/渠道后台（当前无授权，全部 `NoActionRecord` 或 Action Intent）；不做客服话术（异常引发的客户沟通归 SCN-015 关联 Case）；不做账号健康指标治理（SCN-018）。
- 不适用：无订单/物流追踪数据基线的渠道（先建数据接入再谈监测）；已知平台侧故障且无我方可执行动作（记录观察不建处置 Case）。

## 触发与输入

### 触发

- 经营节奏：每日异常扫描、周度异常复盘、大促期间小时级监测。
- 信号触发：订单状态超时未流转、承运商轨迹停滞/异常、清关延误告警、渠道库存同步偏差、Listing 被抑制/变体错误、跟卖信号、渠道 API 错误率上升、退货率/缺货率异常联动。
- 结构触发：同一环节异常聚集（指向系统性问题而非个案）、异常跨渠道同现（指向供应商/物流商问题）、异常与促销/大补货时间重叠。

## 业务闭环

1. **STG-01 信号接收**：异常按「渠道×环节×类型」三维聚合；订单/物流/渠道三类信号源分别建档；疑似升级事件标 `flow07_candidate`。
2. **STG-02 建单**：Case Charter 固定主价值流（FLOW-03 为主，FLOW-04/05/07 按异常性质选一，不可兼）、主场景 SCN-014、范围（渠道/SKU/异常类型/时间窗）、处置权限上限声明。
3. **STG-03 上下文装配**：固定对应岗位 Release Bundle；装载异常诊断与根因分类 Skills；只读订单/物流/渠道/库存工具；渠道 SLA 与规则版本。
4. **STG-04 证据与诊断**：业务贡献方产出 Exception Evidence Pack（异常清单、轨迹节点、渠道状态快照、时间线、关联工单）；诊断定位到具体环节并分类根因——「系统同步故障」「仓储操作失误」「承运商/清关延误」「渠道规则变更」「供应商缺货」「我方流程缺陷」；同类聚集时标记 `systemic_candidate`。
5. **STG-05 方案产物**：「异常处置包」——逐异常处置建议（重发/退款/升级渠道工单/listing 修复/库存重映射）、客户沟通要点（移交 SCN-015）、根因反馈建议（移交 FLOW-03 计划/SCN-015 话术/FLOW-04 渠道配置）、预防措施；每条标注可证伪条件。
6. **STG-06 Assurance 门禁**：确定性校验（异常分类 schema、处置权限、成本上限、时效 SLA、口径一致）+ AGT-005 语义复核（定位是否有轨迹证据、根因分类是否跳步、反馈建议是否可执行）。
7. **STG-07 受控动作**：获批方案拆为逐对象 Action Intent → Policy Gate 判定 → Execution Broker 执行 → 逐对象回执（重发已创建/退款已执行/渠道工单已提交/listing 已修复）；拒绝/异常记入 Case Ledger。当前阶段无授权连接时全部 `NoActionRecord`。
8. **STG-08 核验与关闭**：处置回执与异常消除核验（状态回归正常）；根因反馈确认已被上游 Case/流程接收；周期性异常率复盘；关闭后学习提取回流监测规则。

## 授权与例外

- **允许**：只读订单/物流/渠道/库存数据；产出诊断、处置建议、Action Intent 与根因反馈；跨 Case 引用已验收 Artifact。
- **冻结条件**：订单/物流数据源不可用且无法交叉验证；渠道 API 故障期间无法确认真实状态；异常量超出 Case 处理容量且未分级；疑似账号健康事件但 SCN-018 Case 未建立。
- **高风险动作分级**：批量重发/退款、渠道官方工单升级、listing 大规模修改、涉及清关申报变更——逐对象单独审批。
- **歧义处理**：异常无法定位到具体环节时记 `unresolved_location` 并扩大证据范围而非猜测归因；多渠道同现异常优先假设外部共同原因（物流商/供应商）而非分别归因。
- **重复与部分失败**：同 `case_dedupe_key` 关联既有 Case；部分数据源缺失时只冻结受影响环节分支；Worker 产物不合格退回 STG-04。

## 接管与恢复

- 停止条件：连续两轮补证不满足最小输入；发现异常被误分类导致错误处置；渠道/承运商系统性故障扩大；异常率超阈值且无降级方案。
- 冻结范围：仅冻结受影响渠道/环节/异常类型；已执行的 Action Intent 由执行方 Recovery Contract 负责（重发可拦截、退款可冲正、渠道工单可撤回评估），本 Case 只引用回执。
- 已产生外部效果：重发订单、退款、渠道工单、listing 修改——需逐对象回执可对账；处置后异常仍存在的记 `residual_anomaly` 进入再诊断，不得重复处置同一异常。
- 恢复：冻结解除后从断点继续；Exception Evidence Pack 版本化保留；根因反馈未被接收的异常保持 `feedback_pending` 状态直至确认。

## 验收与经济性

- **产物验收**：Evidence Pack 轨迹/快照证据覆盖率 100%；每个处置建议带环节定位与证据引用；根因分类六类中必须选一并给依据；反馈建议明确标注接收方 Case/流程。
- **经营指标**：异常发现时长（MTTD）、定位时长、处置时长（MTTR）、异常率趋势、重复异常率、因异常导致的 GMV 损失与账号指标影响估算。
- **双层 KPI 关系**：FLOW-03 绑定时看交付异常率与履约成本；客户体验影响经 `correlation_id` 移交 FLOW-05 Case；账号健康影响升级 SCN-018；品牌资产影响（体验折损）移交 FLOW-09。本 Case 不背品牌结果。
- **经济性门槛**：首个周期以「异常定位准确率经抽样复核 + 所有处置动作可对账 + 至少一类根因反馈被上游实际采纳」为验收前提。
- **必须回放**：无轨迹证据的环节定位（应被证据检查拦截）；把渠道 API 故障误判为我方缺货（应被多源交叉验证拦截）；同一异常重复处置（应被 `residual_anomaly` 规则拦截）；根因反馈无人接收仍关闭 Case（应被 `feedback_pending` 状态拦截）；跨渠道异常率被直接平均（应被口径规则拦截）。
